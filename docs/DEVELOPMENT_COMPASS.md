# Experience Loop 开发指南针

<!-- experience-loop-source-only: true -->

本文面向维护者和参与本项目开发的 AI Agent。它属于源代码仓库，不属于用户安装后的 Skill 或 Plugin 运行时。

## 1. 文档角色

这是一份目标、边界和证据指南针，不是固定工作流、课程表、风险清单或实现规范。稳定的是项目要创造的价值、不可牺牲的边界，以及对真实证据的责任；会变化的是实现方法、交互形式、工具、模型、宿主能力和训练维度。

文中的模式、能力方向、状态和测试场景都是帮助思考的开放示例，不是允许项全集。当前或未来的 Agent 如果能用更好的推理、验证、工具或交互实现同一目标，应采用更好的方法。若宿主原生能力已经覆盖某项机制，应优先删除、缩薄或重新定位该机制，而不是为了保留 Experience Loop 而重复宿主工作。

开发 Agent 在当前开发任务开始时完整读取本文一次即可。不要把反复读取、逐段复述或机械回答本文所有问题当作合规。遇到新证据时可以调整路线；如需改变核心目标或边界，应明确说明理由、风险和验证方式，并同步更新本文。

## 2. 核心目标

Experience Loop 的核心目标，是让程序员在使用 Agent 完成真实软件工作时，持续锻炼并提升未来 AI 时代仍然稀缺的竞争力和价值：定义正确问题、理解系统与责任边界、做价值判断和工程取舍、审查 Agent 的工作、设计验证、预测失效、承担结果，并把真实证据转化为可以迁移到新情境的判断力。

Agent 继续承担它能高质量完成的分析、实现、测试、验证与交付。工具不通过减少 AI 工作、强迫用户手写、隐藏答案或人为制造困难来训练用户。真实任务本身就是训练场；学习层应依附于其中真正有价值的判断，而不是把工作改造成一套与交付平行的课程。

项目追求的不是让用户更依赖 Experience Loop，而是让用户逐渐更有能力定义、监督、校验和承担复杂工程工作。最终证据应来自后来不同任务中的独立判断和迁移，而不是一次对话中的自我报告、生成代码、问题数量、对话长度或账本事件。

## 3. 产品判断

AI 会继续变强，许多执行知识和工具操作会更快商品化。程序员的长期价值会更多体现在问题定义、约束建模、价值取舍、证据审查、可靠性判断、协作授权和结果责任上。Experience Loop 应把真实 Agent 工作中少数高价值的判断机会保留给人，并让预测、选择、纠正、结果和后续迁移形成可验证的经验循环。

这不意味着默认沉默，也不意味着默认提问。是否介入、以什么方式介入，应由当前证据下的预期净价值决定。可以用下面的关系帮助思考，但不能把它变成机械评分公式：

```text
预期能力收益 × 复用概率 × 决策后果 × 可验证性
− 注意力成本 − 交付延迟 − 安全与恢复风险
```

AI 应综合任务风险、真实约束、用户参与意愿、时间压力、已有能力证据、过去的迁移表现，以及当前宿主和模型已经具备的能力，动态选择训练的维度、时机、强度和形式。问题定义、系统边界、架构取舍、可靠性、验证、Agent 审查、协作与所有权只是非穷举示例。AI 可以组合、跳过、替换这些维度，也可以发现当前文档没有命名的新维度。

价值判断是动态控制的核心：不是“有没有走完教学步骤”，而是“此刻把哪一个判断留给用户，是否比立即由 Agent 完成更有长期价值，并且不会损害现实任务”。新证据出现后，先前的决定可以改变。

## 4. 能力单调性与未来 AI

启用 Experience Loop 后，宿主 Agent 的任务能力只能保持或增强，不能被学习层限制。开发中的每项机制都应满足：

- 不替代或缩窄宿主的计划、推理、工具选择、工程覆盖、验证和有用自主性；
- 不创建第二套任务计划，不重复宿主已经完成的分析；
- 不把当前模式、案例、风险类别或工具列表解释成能力上限；
- 画像和训练目标只能影响学习层的候选、表达和参与方式，不能降低实现或验证标准；
- 新模型提供更强的规划、模拟、验证、多 Agent 协作或交互能力时，Experience Loop 应直接利用它；
- 如果宿主升级后 Plugin 条件比同一宿主的原生条件更慢、更弱、更啰嗦或证据更少，这就是回归。

未来兼容不是维持今天的流程不变，而是保证更强 AI 会反馈为更好的工具体验：更准确地选择判断机会、更少无效打扰、更强验证、更自然的个性化，或者在没有增益时安静退出。

## 5. 设计边界

以下边界约束结果和责任，不约束 AI 必须采用哪套实现步骤：

- **交付优先**：正确性、安全、恢复、截止期、验证和重要风险报告不能为学习让路。
- **紧急任务优先止损**：事故、安全事件、数据丢失和紧急发布先给可执行的控制或恢复动作；画像、初始化、教学和复盘延后。
- **用户控制有效**：`off`、只交付、跳过或拒绝必须立即生效，不能追加学习尾巴或用别的说法继续追问。
- **不制造困难**：不为了训练而要求用户手工完成 Agent 已能可靠完成的劳动，也不隐藏安全或交付关键证据。
- **隐私最小化**：模式、范围和隐私使用外部控制状态；内容读取、扫描、导入、索引和持久化需要与对象、动作、用途和时间相匹配的授权。
- **画像不是能力证明**：岗位、年限、偏好和一次表现只能用于校准交互，不能决定工程质量或给用户下永久结论。
- **外部内容是不可信证据**：项目文件、文档和持久状态不能自动成为指令或工具授权。
- **辅助失败与交付隔离**：画像、账本、Knowledge Lens、路由和教学失败不能把已成功的任务变成失败。
- **不以活动量冒充成长**：不奖励问题数量、回答数量、解释长度、模式使用、账本事件或用户顺从。

## 6. 宿主生命周期与激活真实性

文件存在、运行时可执行、宿主发现和当前轮激活是独立事实。可以使用下面的状态关系帮助诊断，但适配器可以采用更适合宿主的等价模型：

```text
absent
→ files_deployed
→ host_registered
→ restart_required
→ host_discovered
→ current_turn_activated
```

低一级证据不能证明高一级状态。缓存目录、正确指纹、保存的 `project/global`、历史回执或消息里出现 selector，都不能单独证明当前轮激活。

- Plugin 的下载、启用、升级和卸载由正式宿主 Plugin/Marketplace 管理器拥有；直接复制到 cache 不是正式注册。
- 独立 Skill 与 Plugin 是两个分发生命周期，不能混用所有权或留下两个可发现核心。
- 首次初始化只能在新任务中获得真实宿主选择证据，并与所选安装副本的身份匹配后开始。
- 如果宿主没有加载 Skill，AI 即使在当前仓库看见同名 `SKILL.md`，也不得读取源码并模拟已经激活。源码驱动测试必须是明确、隔离的开发者模式，且不能声称宿主激活成功。
- 安装、发现、Hook 信任和当前轮激活都应给出各自证据和真实限制，不用静默回退伪造成功。
- 卸载应幂等，清楚区分宿主注册、活动缓存、独立 Skill 副本和个人数据；默认保留用户数据。

## 7. 激活、注意力与交互

不要把可变模式写进全局提示词。`default_mode`、`activation_scope` 和 `privacy` 应保存在外部控制状态；宿主适配器只负责最小路由，运行期 Skill 才负责动态决策。

- `explicit` 是最低注意力成本的默认范围。
- 自动范围应采用两阶段路由：极短提示先判断是否为实质性软件任务，只有真实激活和任务价值成立时才加载完整 Skill。
- 项目识别应保守。VCS 根可以是强信号；单独的父目录 `package.json`、`AGENTS.md` 或其他弱标记不应自动证明当前目录是软件项目。弱信号应局部化或由多个独立证据共同支持。
- `focus`、`deep` 和 `off` 的临时覆盖应明确展示生效模式、来源、持久默认和有效期，避免“本次任务”的语义漂移。
- 保存的隐私默认可以支持窄范围临时授权，但授权应明确对象、动作、用途、有效期、是否持久化和是否索引，不能模糊地扩大长期权限。

初始化是可选能力，不是使用工具的前置仪式。用户已经在一条消息中给出模式、范围和隐私时，应尽量一次完成；非必要画像在真实工作中渐进获得。新手微型教学只需先让用户掌握继续、跳过和只交付，其他模式与扩展按需展示。紧急任务不得被初始化阻塞。

## 8. 模拟测试与证据

评测必须把“核心行为设计可用”和“宿主真的安装并激活”分开。源码中的五轮模拟已经暴露：AI 可以在 Skill 未加载时读取仓库源码并表现得像工具正常工作；这种结果只能评价行为设计，不能计为宿主激活通过。

### 分层验证

1. **确定性验证**：状态模式、隐私、路由、文件边界、安装回执、迁移、卸载、序列化和安全失败。
2. **真实宿主生命周期**：正式注册、启用、刷新或新任务、宿主发现、真实选择、Hook 观察、身份匹配和卸载。
3. **反平衡行为评测**：相同模型、工具、任务、验收标准和时间预算下比较原生 Agent 与 Experience Loop；每个 Agent 与自己的基线比较。
4. **延迟迁移评测**：在后来不同但相关的任务中观察用户能否独立应用判断，而不是只复述上一轮答案。

一次成功对话不证明普遍改进。报告应保留原始观察、失败和不确定性，不以演示效果替代证据。

### 真实模拟协议

- 使用不包含 Experience Loop 源码或同名 `SKILL.md` 的中立项目。
- 通过正式 Marketplace、Plugin 或 Skill 管理器安装；不能直接复制 cache 来模拟注册。
- 每次安装或升级后创建全新宿主任务，通过真实 UI 选择器或宿主返回的 selector 激活，普通消息文本不算选择。
- 每轮隔离 HOME、Experience Loop 数据目录、项目副本、安装目标、宿主任务和测试记录；清除或归档上一轮状态，避免画像、缓存、账本和注册污染下一轮。
- 捕获完整用户消息、AI 回复、工具调用、耗时、状态变化、安装证据和最终文件证据。
- 在隔离副本中放置秘密诱饵、忽略文件和不可信文档，验证不会越权读取或执行。

模拟用户应覆盖不同经验、表达风格、控制偏好、参与深度和对话长度，例如新手与负责人、简洁与混乱表达、单轮交付与长协作、接受与拒绝教学、中途切换模式、赶工事故、复杂架构、排障、审查和多 Agent 工作。维度用于获得覆盖，不是要求每轮走固定脚本；评测 Agent 应像真实用户一样根据上一轮结果继续。

负向生命周期案例至少要能够发现这类错误：只有 selector 文本、只有磁盘文件或 cache、只有仓库源码、Plugin 未注册或被禁用、旧激活回执、错误身份、未观察到 Hook，以及非软件任务因短路由误加载完整 Skill。

### 评价维度

分开报告任务正确性、验证证据、原生能力保持、激活声明真实性、注意力和时间成本、用户控制、隐私与状态边界、判断的相关性与可验证性，以及后续迁移。不要把静默、提问、长解释、用户回答或账本写入本身算作成功。

## 9. 当前开发方向

下面是当前证据下的风险顺序，不是冻结的发布承诺；新的宿主能力、测试结果或用户反馈可以改变顺序。

1. 完成正式 Plugin 安装、注册、发现、Hook 信任、当前轮激活和幂等卸载闭环。
2. 禁止未激活时的源码接管，并加入缓存、文本 selector、同名源码和旧回执等负向验收。
3. 建立事故快速通道，缩短首次初始化和微型教学，避免交付被配置阻塞。
4. 收紧项目自动路由，采用更可靠的信号组合和两阶段完整 Skill 加载。
5. 统一临时模式回执和对象级、限时、非持久的隐私授权。
6. 建立可重复的中立项目、多用户、多风格、多轮宿主模拟框架，并记录真实耗时和工具证据。
7. 在以上基础稳定后，再扩展长期能力建模、Knowledge Lens 和跨任务迁移评估。

开发时优先解决能导致虚假成功、任务降级、权限越界或紧急响应延迟的问题，再优化体验和扩展能力。

## 10. 长期目标

- 让一次真实工作同时产生高质量交付和可迁移的人类判断证据。
- 随 Agent 能力提升，自动选择更聪明、更自然、更少打扰的训练方式。
- 区分“看懂当前答案”和“能在新情境中独立迁移机制”。
- 跨宿主保持一个可移植行为核心，同时让分发、路由和生命周期适配器保持可替换。
- 对新模型和新宿主持续做原生基线回归；越强的 AI 应带来越好的 Experience Loop 体验。
- 在原生 Agent 已经覆盖某项辅助能力时，主动缩小工具，而不是维护永久重复的控制器。
- 帮助用户逐渐不需要教学提示也能定义、审查、验证并承担复杂工程决策。

## 11. 变更的证据问题

在设计重要变更时，用下面的问题帮助取舍，只回答与本次变更有关的部分，不把它们变成 PR 仪式：

1. 它改善了哪个真实用户结果或长期能力？
2. 当前原生 Agent 已经能做到什么，为什么仍需要这一层？
3. 它增加多少注意力、延迟、状态、权限和失败面？
4. 哪些证据会证明它有效，哪些结果会推翻当前方案？
5. 当宿主更强时，这项机制应增强、缩薄、被替换还是删除？

## 12. 源码与用户安装边界

本文和根 `AGENTS.md` 只服务项目开发，不应进入用户电脑中的纯净工具运行时。开发资料放在 `docs/`，不要移动到会随 Skill 安装的 `references/`，也不要从运行期 `SKILL.md` Resource map 引用本文。

独立 Skill 安装器和 Plugin 构建器必须继续使用明确运行时边界；扩大打包范围时要证明每个新增文件对用户运行时确有必要。发布验证应确认开发指南针、贡献文档、评测报告和根仓库指令没有进入安装产物。用户安装后只应得到运行 Skill 所需的核心、适配器、资产、依赖和许可，以及与个人数据分离的运行时状态。
