# Capability compass

Use this reference when choosing the one capability worth strengthening in a task, interpreting ledger evidence, preserving fundamentals, or discussing longer-term growth.

## Principle

Optimize for increasingly independent judgment under real constraints, not for generated-code volume, prompt fluency, or coverage of a curriculum.

Keep the compass internal during ordinary work. The user should not need to choose categories or maintain a skill matrix.

Selecting one direction limits only the learning seam and ledger label. It must never narrow engineering inspection, testing, security review, reliability work, or acceptance coverage. A task may require many engineering concerns while highlighting only one reusable human judgment.

## Six directions

### Problem framing (`problem-framing`)

Strengthen the ability to identify the real user or business problem, define goals and non-goals, expose constraints, write executable specifications, and decide what evidence would count as success.

Prefer this direction when the main risk is building the wrong thing, accepting an underspecified request, or optimizing a technical metric that is disconnected from value.

### System modeling (`system-modeling`)

Strengthen fundamentals, code reading, architecture, data flow, state, integration, domain constraints, performance mechanisms, and the ability to move one level above and below a local change.

Prefer this direction when the main risk is misunderstanding ownership, hidden invariants, dependency direction, runtime behavior, or the wider system impact.

### Verification (`verification`)

Strengthen test design, evaluation, debugging, causal reasoning, code review, falsification, and cognitive coverage.

Prefer this direction when an answer is “almost correct,” tests may pass for the wrong reason, the root cause is uncertain, or acceptance claims exceed the evidence.

### Reliability (`reliability`)

Strengthen security, least privilege, privacy, observability, incident response, rollout, rollback, capacity, performance, dependency, and supply-chain judgment.

Prefer this direction when failure can expose data, break production, create irreversible state, or be difficult to detect and recover from.

### Agent leverage (`agent-leverage`)

Strengthen task selection, delegation, decomposition, context design, tools, permissions, feedback loops, multi-Agent coordination, failure recovery, and net-cost calibration.

Prefer this direction when the important question is whether to use an Agent, deterministic automation, a human decision, or several bounded workers—and how to make that choice reliable next time.

### Ownership (`ownership`)

Strengthen end-to-end responsibility, domain depth, real-user and production feedback, communication, technical leadership, mentoring, prioritization, and agency.

Prefer this direction when local implementation is not enough and someone must connect the change to adoption, operations, cross-team consequences, or long-term outcomes.

## Select without adding friction

For each non-trivial task:

1. Identify the judgment that most affects correctness, user value, safety, or recovery.
2. Map it to one direction; do not split attention across all six.
3. Prefer a direction that recurs in the user's responsibilities or domains when an authorized profile makes that relevant.
4. Use prior ledger evidence only as a tie-breaker. One missing category is not automatically a gap.
5. Prefer a chance for stronger evidence—independent prediction, correction, verification, or transfer—over another explanation.
6. In `auto`, skip capability work when no durable judgment exists or interruption cost exceeds concrete current or future value.

Do not announce the selected direction unless it helps the user review the result or they asked for a growth explanation.

## Preserve fundamentals without creating homework

Do not equate “the Agent implemented it” with lost learning. Preserve the human mental model through one high-value act such as:

- predict the owning layer or failure mechanism;
- explain one invariant in plain language;
- choose evidence that could falsify the leading hypothesis;
- review one boundary, state transition, or rollback path;
- compare the expected and observed system behavior.

Suggest a short no-Agent ownership exercise only when several evidence-bearing tasks show the same dependency on scaffolding, or when the user explicitly requests deliberate practice. Keep it optional, bounded, and attached to a real responsibility.

## Interpret capability evidence

Treat ledger summaries as observations, not scores:

- repeated guided events show exposure and practice, not independence;
- independent verification and caught-Agent errors are stronger than smooth execution;
- transfer across a different project, technology, constraint, or role is stronger than repetition;
- missing events may mean missing opportunity or missing recording, not weak capability;
- recent contradictions should lower confidence more than old successes raise it.

Never rank the user, compare them with other people, or claim mastery from counts.

## Review a longer trajectory

Run a trajectory review only when the user asks or a natural milestone provides several real contexts. Summarize:

1. outcomes and responsibilities already handled;
2. decisions increasingly owned with less scaffolding;
3. strongest verification, correction, and transfer evidence;
4. one recurring blind spot or evidence gap, with uncertainty;
5. one next real responsibility that compounds future value;
6. one depth bet tied to the user's domain or system, not a generic tool trend.

Prefer movement toward problem ownership, system understanding, evidence, production responsibility, Agent harness design, and domain depth. Do not prescribe a long course catalog or chase every new model and editor.
